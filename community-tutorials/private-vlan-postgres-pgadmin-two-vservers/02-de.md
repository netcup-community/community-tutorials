# Einführung

Eine Datenbank direkt im öffentlichen Internet zu betreiben ist einer der häufigsten Wege, wie Server kompromittiert werden. Jeder offene PostgreSQL-Port ist ein Ziel für Brute-Force-Login-Versuche und Exploits. Der sicherste Datenbankserver ist einer, der überhaupt keine öffentliche IP-Adresse hat.

In diesem Tutorial bauen wir genau das. Wir verwenden zwei netcup vServer, die über ein **Cloud vLAN** verbunden sind (ein virtuelles lokales Netzwerk - ein privates Netzwerk, das nur deine eigenen Server sehen können):

- Ein **Edge-Server** mit öffentlicher IP-Adresse. Er ist klein (1 Kern, 1 GB RAM), betreibt **pgAdmin** (ein webbasiertes Administrationstool für PostgreSQL) und fungiert als einziger, gehärteter Einstiegspunkt in dein Setup. Zusätzlich arbeitet er als **NAT-Gateway** (Network Address Translation - er lässt den privaten Server über die öffentliche IP des Edge-Servers auf das Internet zugreifen), damit der Datenbankserver weiterhin Paket-Updates herunterladen kann.
- Ein **Datenbankserver** mit mehr Ressourcen (4 Kerne, 8 GB RAM), der **PostgreSQL** betreibt und **keine öffentliche IP-Adresse** hat. Er ist nur über das private Cloud vLAN erreichbar.

Die resultierende Architektur sieht so aus:

```
                 Internet
                    |
        public IPv4/IPv6  (ufw: SSH + HTTPS)
                    |
        +-----------------------+          Cloud vLAN 10.132.0.0/24
        |  EDGE  (1 core/1 GB)  | eth1: 10.132.0.10 -----+
        |  - pgAdmin4 (web)     |                        |
        |  - NAT gateway        |                        |
        +-----------------------+                        |
                                                         |
        +-----------------------+                        |
        |  DB  (4 core/8 GB)    | eth1: 10.132.0.20 -----+
        |  - PostgreSQL         |   (NO public IP)
        |  - default route -> 10.132.0.10 (NAT)
        +-----------------------+
```

Die Lesezeit dieses Tutorials beträgt etwa 15 Minuten; die Umsetzung dauert ungefähr 90 Minuten.

Alle Beispiele wurden im Juli 2026 auf **Debian 13 (Trixie)** getestet und lassen sich mit kleinen Anpassungen auf andere Distributionen übertragen. Im gesamten Tutorial werden die beiden Server als **s-edge** (der öffentliche Edge-Server) und **s-db** (der private Datenbankserver) bezeichnet. Muss ein Befehl auf beiden Servern ausgeführt werden, wird das explizit angegeben; andernfalls gehört er nur zum genannten Server.

Das Tutorial verwendet die beispielhaften privaten IP-Adressen `10.132.0.10` (s-edge) und `10.132.0.20` (s-db) sowie den Platzhalter `<edge-public-ip>` für die öffentliche IP-Adresse des Edge-Servers. Ersetze diese beim Durcharbeiten durch deine eigenen Werte.

# Anforderungen

- Zwei netcup vServer, beide mit Debian 13:
  - **s-edge** - der Edge-Server, 1 Kern / 1 GB RAM sind ausreichend, z. B. [VPS pico G11s](https://www.netcup.com/de/server/vps/vps-pico-g11s-12m-nue).
  - **s-db** - der Datenbankserver, 4 Kerne / 8 GB RAM wie für eine PostgreSQL-Workload empfohlen, z. B. [VPS Lite 2 G12s](https://www.netcup.com/de/server/vps/vps-lite-2-g12s-3m).
- Ein [Cloud vLAN Free](https://www.netcup.com/de/erweiterungen-kvm/cloud-vlan-free-nue) (oder höher), das beiden Servern hinzugefügt wurde.
- Zugang zu deinem [Customer Control Panel (CCP)](https://www.customercontrolpanel.de) und [Server Control Panel (SCP)](https://www.servercontrolpanel.de).
- Ein Benutzer mit Root-Rechten (`sudo`) auf beiden Servern.

Dieses Tutorial setzt voraus, dass du die oben genannten Produkte bereits bestellt und die grundlegende Server-Härtung bereits durchgeführt hast. Falls du deine Server noch nicht mit SSH-Key-Authentifizierung und einem Nicht-Root-Benutzer abgesichert hast, folge zuerst auf **beiden** Servern dem Tutorial [Erste Schritte zum Schutz deines Linux-Servers](https://community.netcup.com/de/tutorials/first-steps-to-protect-your-linux-server-against-common-attacks). Wir bauen die Firewall hier auf dieser Basis auf.

> **Info**
> Ein Cloud vLAN Free ist ein privates Layer-2-Netzwerk. Jeder Server, den du an dasselbe vLAN anschließt, kann mit jedem anderen darin kommunizieren, isoliert vom öffentlichen Internet und von anderen netcup-Kunden.

# Schritt 1 - Das Cloud vLAN im SCP anschließen

Gib zunächst jedem Server eine zweite Netzwerkschnittstelle, die mit deinem Cloud vLAN verbunden ist. Dies erfolgt vollständig im webbasierten Server Control Panel (SCP).

1. Melde dich in deinem [SCP](https://www.servercontrolpanel.de) an, entweder direkt oder über die Autologin-Funktion in deinem [CCP](https://www.customercontrolpanel.de).
2. Wähle **s-edge** aus der Serverliste oben links.
3. Navigiere im linken Seitenmenü zum Bereich **Netzwerk**.
4. Wähle oben rechts **Ethernet-Schnittstelle hinzufügen**.
5. Wähle dein Cloud vLAN aus und als Treiber **virtio**.
6. Wiederhole Schritte 2–5 für **s-db** und fahre dann mit Schritt 2 fort.

Nach einem Neustart (oder einem Netzwerk-Restart, siehe unten) hat jeder Server eine neue Schnittstelle für das vLAN. Bei netcup-Debian-Images ist das üblicherweise `eth1`, kann aber auch als `ens7` oder ähnlich erscheinen. Prüfe den genauen Namen mit `ip addr`, bevor du fortfährst.

# Schritt 2 - Die vLAN-Schnittstelle konfigurieren

Die neue Schnittstelle hat noch keine IP-Adresse. Wir weisen statische private Adressen über den klassischen `ifupdown`-Netzwerkstack zu, der von netcups Debian-Images verwendet wird.

Bei einer minimalen Installation ist `ifupdown` möglicherweise nicht vorhanden. Installiere es bei Bedarf auf **beiden Servern**:

```bash
sudo apt update
sudo apt install ifupdown
```

## Schritt 2.1 - s-edge konfigurieren

Erstelle auf **s-edge** die vLAN-Konfiguration mit deinem bevorzugten Texteditor, z. B. `sudo nano /etc/network/interfaces.d/vlan.cfg`:

```
auto eth1
iface eth1 inet static
    address 10.132.0.10
    netmask 255.255.255.0
```

## Schritt 2.2 - s-db konfigurieren

Erstelle auf **s-db** dieselbe Datei, jedoch mit der zweiten Adresse. Da s-db keine öffentliche IP hat, braucht er zusätzlich den Edge-Server als **Standard-Gateway** (die Route, über die aller internetgebundene Verkehr das System verlässt) sowie DNS-Resolver (die Hostnamen wie `deb.debian.org` in IP-Adressen übersetzen):

```
auto eth1
iface eth1 inet static
    address 10.132.0.20
    netmask 255.255.255.0
    gateway 10.132.0.10
    dns-nameservers 46.38.225.230 46.38.252.230
```

> **Info**
> `46.38.225.230` und `46.38.252.230` sind die öffentlichen IPv4-DNS-Resolver von netcup.

## Schritt 2.3 - Netzwerk neu starten

Wende die Konfiguration auf **beiden Servern** an:

```bash
sudo systemctl restart networking
```

# Schritt 3 - vLAN-Konnektivität prüfen

Bevor du weitermachst, bestätige, dass das private Netzwerk tatsächlich funktioniert.

Prüfe auf **s-edge**, ob die Schnittstelle ihre Adresse hat:

```bash
ip addr show eth1
```

Du solltest `inet 10.132.0.10/24` auf der Schnittstelle sehen. Pinge nun s-db über das vLAN an:

```bash
ping 10.132.0.20 -c 5
```

```
PING 10.132.0.20 (10.132.0.20) 56(84) bytes of data.
64 bytes from 10.132.0.20: icmp_seq=1 ttl=64 time=0.450 ms
64 bytes from 10.132.0.20: icmp_seq=2 ttl=64 time=0.510 ms
...
--- 10.132.0.20 ping statistics ---
5 packets transmitted, 5 received, 0% packet loss, time 104ms
```

Führe anschließend den umgekehrten Ping von **s-db** zu `10.132.0.10` aus, um zu bestätigen, dass die Verbindung in beide Richtungen funktioniert. Sobald beide Richtungen erfolgreich sind, ist das vLAN bereit.

# Schritt 4 - Den Edge-Server zum NAT-Gateway machen

Der Datenbankserver hat keine öffentliche IP und kann daher von sich aus nicht für Paket-Updates auf das Internet zugreifen. Wir lösen das, indem wir **s-edge** zu einem NAT-Gateway machen: Er leitet den ausgehenden Verkehr von s-db weiter und schreibt ihn so um, dass er seine eigene öffentliche IP verwendet.

Alle Befehle in diesem Schritt laufen auf **s-edge**.

## Schritt 4.1 - IP-Forwarding aktivieren

Standardmäßig leitet Linux keine Pakete zwischen Schnittstellen weiter. Aktiviere dies. Bearbeite `/etc/sysctl.conf`, z. B. mit `sudo nano /etc/sysctl.conf`, und stelle sicher, dass diese Zeile vorhanden und nicht auskommentiert ist:

```
net.ipv4.ip_forward = 1
```

Wende die Änderung sofort an:

```bash
sudo sysctl -p
```

## Schritt 4.2 - NAT in ufw konfigurieren

Wir verwalten Firewall und NAT mit **ufw** (Uncomplicated Firewall). Erlaube zunächst weitergeleiteten Verkehr. Bearbeite `/etc/default/ufw`, z. B. mit `sudo nano /etc/default/ufw`, und ändere die Forward-Policy:

```
DEFAULT_FORWARD_POLICY="ACCEPT"
```

Füge als Nächstes die NAT-Masquerade-Regel hinzu. Bearbeite `/etc/ufw/before.rules`, z. B. mit `sudo nano /etc/ufw/before.rules`, und fügen den folgenden Block **ganz am Anfang der Datei** ein, vor der bestehenden `*filter`-Zeile. Ersetze `eth0` durch deine öffentliche Schnittstelle und `eth1` durch deine vLAN-Schnittstelle, falls diese abweichen:

```
*nat
:POSTROUTING ACCEPT [0:0]
# Masquerade traffic from the Cloud vLAN going out via the public interface
-A POSTROUTING -s 10.132.0.0/24 -o eth0 -j MASQUERADE
COMMIT
```

Lade ufw neu, um die Änderung anzuwenden (falls ufw noch nicht aktiviert ist, geschieht dies in Schritt 7 - die Regel greift, sobald es aktiviert ist):

```bash
sudo ufw reload
```

## Schritt 4.3 - Internetzugang von s-db prüfen

Bestätige auf **s-db**, dass es jetzt über das Gateway auf das Internet zugreifen kann:

```bash
ping 1.1.1.1 -c 3
sudo apt update
```

Beide sollten erfolgreich sein, obwohl s-db weiterhin keine nennenswerte öffentliche Präsenz hat. Wenn `apt update` bei der DNS-Auflösung hängen bleibt, überprüfe erneut die Zeile `dns-nameservers` aus Schritt 2.2.

# Schritt 5 - PostgreSQL installieren und konfigurieren

Alle Befehle in diesem Schritt laufen auf **s-db**.

## Schritt 5.1 - PostgreSQL installieren

```bash
sudo apt update
sudo apt install postgresql
```

## Schritt 5.2 - PostgreSQL nur an das vLAN binden

Standardmäßig lauscht PostgreSQL nur auf `localhost`. Wir wollen, dass es **nur auf der privaten vLAN-Adresse** lauscht - niemals auf `*` (alle Schnittstellen) und niemals auf einer öffentlichen IP. Diese eine Einstellung ist es, die die Datenbank von jedem öffentlichen Netzwerk fernhält.

Finde den Speicherort deiner Konfigurationsdatei:

```bash
sudo -u postgres psql -c 'SHOW config_file;'
```

Auf Debian 13 ist das typischerweise `/etc/postgresql/17/main/postgresql.conf`. Bearbeite sie und setze:

```
listen_addresses = '10.132.0.20'
```

## Schritt 5.3 - Dem Edge-Server die Verbindung erlauben

Bearbeite `pg_hba.conf` im selben Verzeichnis (z. B. `/etc/postgresql/17/main/pg_hba.conf`). Diese Datei (`pg_hba` steht für "host-based authentication") steuert, welche Clients sich verbinden dürfen. Füge eine Zeile hinzu, die **ausschließlich** die vLAN-Adresse des Edge-Servers zulässt, mit verschlüsselter Passwort-Authentifizierung:

```
# TYPE  DATABASE  USER  ADDRESS          METHOD
host    all       all   10.132.0.10/32   scram-sha-256
```

## Schritt 5.4 - Datenbank und Rolle erstellen

Erstelle eine Anwendungsrolle (Benutzer) und eine Datenbank dafür. Ersetze das Beispielpasswort durch ein starkes Passwort:

```bash
sudo -u postgres psql
```

```sql
CREATE ROLE appuser WITH LOGIN PASSWORD 'changeMe.aHighlyComplexPassword';
CREATE DATABASE appdb OWNER appuser;
\q
```

## Schritt 5.5 - PostgreSQL neu starten

```bash
sudo systemctl restart postgresql
```

Bestätige, dass PostgreSQL jetzt auf der vLAN-Adresse lauscht:

```bash
sudo ss -tlnp | grep 5432
```

Du solltest sehen, dass es an `10.132.0.20:5432` gebunden ist und an nichts sonst.

# Schritt 6 - pgAdmin im Server-Modus installieren

pgAdmin gibt dir eine Weboberfläche zur Verwaltung von PostgreSQL. Wir installieren es nativ im **Server-Modus** (läuft hinter dem Apache-Webserver), was für den 1-GB-Edge-Server leichter ist als ein Container.

Alle Befehle in diesem Schritt laufen auf **s-edge**.

## Schritt 6.1 - Das pgAdmin-Repository hinzufügen und installieren

```bash
# Import the repository signing key
curl -fsS https://www.pgadmin.org/static/packages_pgadmin_org.pub | sudo gpg --dearmor -o /usr/share/keyrings/packages-pgadmin-org.gpg

# Add the repository (uses the Debian codename automatically)
sudo sh -c 'echo "deb [signed-by=/usr/share/keyrings/packages-pgadmin-org.gpg] https://ftp.postgresql.org/pub/pgadmin/pgadmin4/apt/$(lsb_release -cs) pgadmin4 main" > /etc/apt/sources.list.d/pgadmin4.list'

sudo apt update
sudo apt install pgadmin4-web
```

> **Info**
> Falls es für den Debian-13-Codenamen `trixie` noch kein pgAdmin-Paket gibt, ersetze `$(lsb_release -cs)` im obigen Befehl durch den zuletzt unterstützten Codenamen (zum Beispiel `bookworm`).

## Schritt 6.2 - Die Weboberfläche konfigurieren

Führe das Setup-Skript aus. Es konfiguriert Apache und fordert dich auf, einen pgAdmin-Login (E-Mail und Passwort) anzulegen:

```bash
sudo /usr/pgadmin4/bin/setup-web.sh
```

Du kannst pgAdmin nun in deinem Browser unter folgender Adresse öffnen:

```
https://<edge-public-ip>/pgadmin4
```

## Schritt 6.3 - Über das vLAN mit PostgreSQL verbinden

Melde dich bei pgAdmin an und füge dann den Datenbankserver als neue Verbindung hinzu:

- **Host name/address:** `10.132.0.20` (die private vLAN-Adresse von s-db)
- **Port:** `5432`
- **Username:** `appuser`
- **Password:** das Passwort aus Schritt 5.4

Eine ausführliche Anleitung zum pgAdmin-Verbindungsformular findest du im Tutorial [Installing PostgreSQL and pgAdmin with Docker](https://community.netcup.com/de/tutorials/how-to-install-postgres-and-pgadmin-with-docker-and-connect-pgadmin-with-postgres). Die Verbindung läuft vollständig über das private vLAN - sie berührt niemals das öffentliche Internet.

# Schritt 7 - Beide Server mit ufw absichern

Sperre nun beide Server ab. Wir gehen davon aus, dass `ufw` installiert ist (es ist Teil des im Anforderungsabschnitt verlinkten Basis-Härtungs-Tutorials); falls nicht, installiere es auf beiden mit `sudo apt install ufw`.

## Schritt 7.1 - Den Edge-Server absichern

Verweigere auf **s-edge** standardmäßig jeglichen eingehenden Verkehr und erlaube dann nur SSH und die Web-Ports (80 für die Let's-Encrypt-HTTP-Challenge, 443 für pgAdmin über HTTPS):

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
```

## Schritt 7.2 - Den Datenbankserver absichern

Verweigere auf **s-db** jeglichen eingehenden Verkehr und erlaube dann **nur dem Edge-Server**, über das vLAN auf PostgreSQL und SSH zuzugreifen:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.132.0.10 to any port 22 proto tcp
sudo ufw allow from 10.132.0.10 to any port 5432 proto tcp
sudo ufw enable
```

> **Tip**
> Da SSH zu s-db jetzt nur noch vom Edge-Server aus erlaubt ist, erreichst du s-db über den Edge als Jump-Host: `ssh -J operator@<edge-public-ip> operator@10.132.0.20`.

# Fazit

Du hast jetzt einen PostgreSQL-Datenbankserver **ohne öffentliche IP-Adresse**, der nur über ein privates Cloud vLAN erreichbar ist. Die gesamte Administration läuft über einen einzigen, gehärteten Edge-Server: pgAdmin für die Datenbank und ein SSH-Jump-Host für die Shell. Der Edge-Server versorgt die Datenbank außerdem per NAT mit Internetzugang für Updates. Die Angriffsfläche der Datenbank wurde von "das gesamte Internet" auf "einen Server, den du kontrollierst" reduziert.

Einige mögliche nächste Schritte:

- Aktiviere TLS zwischen pgAdmin und PostgreSQL, um auch die Verbindung über das vLAN zu verschlüsseln.
- Installiere [Fail2Ban](https://community.netcup.com/de/tutorials/how-to-install-and-configure-fail2ban-on-a-debian-server) auf dem Edge-Server, um Brute-Force-SSH-Angriffe zu blockieren.
- Richte automatisierte PostgreSQL-Backups auf dem Datenbankserver ein.
